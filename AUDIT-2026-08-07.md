# Meith audit — 7 August 2026

A functional and security audit of the whole board, driven through a real
browser against a real PostgreSQL 16 server. Every finding below was reproduced
in Chromium; nothing here is inferred from reading the code alone, and each one
names the file that causes it.

## How this was run

| | |
|---|---|
| Database | PostgreSQL **16.13**, a real server — *not* PGlite |
| Board | installed from scratch through `/install` in the browser |
| App | `next dev`, `DATA_SOURCE=postgres`, `QUEUE_DRIVER=postgres`, `FILESTORE_DRIVER=local` |
| Browser | Chromium 1194 via Playwright, both with and **without** JavaScript |
| Accounts | administrator, super moderator, three members, one guest |

The real server matters. The whole test suite runs on PGlite, and two of the
findings below are exactly the PGlite-substitution gap `packages/db/src/client.ts`
already warns about — they cannot be reproduced on PGlite at all.

### What passed first

Everything the repository gates on is green, so none of this is a regression the
project's own checks would have caught:

- `pnpm test` — **4584 passed**, 5 skipped, 0 failed (258 files)
- `pnpm test:e2e` — **37 passed** (board and installer projects)
- `pnpm lint`, `pnpm depcruise`, all three `typecheck` projects — clean
- All twelve invariant/generated-doc guards — clean

The audit found **10 gaps**, all of them in places no existing gate looks.

## H1 — Anyone can lock any account out of the board, including the administrator

**Severity: high.** Unauthenticated, no prerequisites, indefinitely repeatable.

`apps/forum/src/server/auth-actions.ts:75`

```ts
function loginBucket(identifier: string): string {
  return `login:${foldIdentifier(identifier)}`
}
```

The lockout bucket is the **username alone**. With `maxLoginAttempts: 5` and
`lockoutMinutes: 15` (`packages/accounts/src/policy.ts:28-29`), five wrong
guesses against a name lock that account for fifteen minutes — for everybody,
from every address, including the real owner with the correct password.

### Reproduced

From a fresh browser context with no session, six bad guesses against
`auditowner` (the board's only administrator):

```
locked after 6 guesses from a fresh session
```

then, in a *different* fresh context, signing in with the correct password:

```
Not saved. Too many failed attempts. Please wait before trying again.
```

Five requests every fifteen minutes denies the administrator their own control
panel for as long as the attacker cares to keep going. Usernames are public —
`/online`, every postbit, and the member list all name them.

The comment above `loginBucket` anticipates half of this ("guessing account A
cannot lock account B") and defers the rest:

> we deliberately do NOT mix in IP here in fixture mode because the demo has no
> proxy header to trust. The Postgres path can compose a richer bucket later
> without touching this action.

But `loginBucket` is the only bucket there is — line 249 calls it unconditionally,
on Postgres as much as on fixtures. The address is already available and already
trusted elsewhere: `remoteAddress()` in `apps/forum/src/server/admin.ts:71` reads
the left-most `x-forwarded-for` entry and the ACP allowlist matches on it.

**Suggested shape of a fix.** Count per `(username, address)` for the lockout and
keep a much looser per-username counter as a backstop, so a distributed attack on
one account is still slowed but a single actor cannot deny service. Whatever the
policy, a legitimate owner must not be lockable by a stranger.

## H2 — The API tokens screen 500s permanently as soon as a token is used, so no token can be revoked

**Severity: high.** Confirmed on real Postgres; invisible on PGlite.

`packages/db/src/api-repo.ts:88`, consumed at
`apps/forum/app/admin/api-tokens/page.tsx:103`

`PostgresApiTokenRepository.listAll()` reads through a raw `db.execute(sql…)`,
asserts the timestamp columns are `Date`:

```ts
)) as unknown as Array<{ …; created_at: Date; last_used_at: Date | null }>
```

and then passes them straight out:

```ts
lastUsedAt: row.last_used_at,
```

They are **not** `Date`s. Under postgres.js with drizzle attached, raw-SQL
timestamps arrive as strings — measured directly against this board:

```
drizzle.execute → 2 created_at type: string String | last_used_at type: string String
```

So the ACP page calls `formatTime(token.lastUsedAt, now)`, `formatTime` calls
`at.toISOString()` (`apps/forum/src/view/time.ts:130`), and the page throws:

```
⨯ TypeError: at.toISOString is not a function
    at AdminApiTokensPage (app/admin/api-tokens/page.tsx:90:30)
 GET /admin/api-tokens 500
```

### Reproduced

1. `/admin/api-tokens` → create a token. Page renders (`last_used_at` is null).
2. Make one API call with it — any endpoint.
3. `/admin/api-tokens` → **HTTP 500, blank page**, and it never recovers,
   because `last_used_at` is now set forever.

The consequence is worse than a broken screen: the revoke button lives on that
page, so **a leaked token cannot be revoked through the UI**. `docs/rest-api.md`
tells operators "revoking the owner's access revokes the token's in the same
instant" — true, but the narrow control is unreachable.

`api-repo.ts` is the **only** repository in `packages/db` that does this. Every
other one converts: `report-repo.ts:87`, `warning-repo.ts:85-87`,
`modcp-repo.ts:317`, `post-writes.ts:85`, `moderation-queue.ts:112`,
`thread-writes.ts:333` all wrap in `new Date(...)`, and `poll-repo.ts:54` types the
column honestly as `Date | string | null`. Fixing this is four `new Date(...)`
calls and a corrected row type.

Nothing caught it because the whole suite runs on PGlite, which returns `Date`
objects here. This is precisely the hazard `client.ts` documents at length for
the *serialise* direction; `restoreDateSerialisers` fixes writes and leaves reads
alone.

**Also latent:** `packages/db/src/outbox-repo.ts:71-72` and `107-108` pass
`created_at` / `dispatched_at` through under the same false `Date` type. Nothing
consumes them as dates today, so no live failure — but it is the same trap armed.

## M3 — Two usergroup permissions are editable, resolved, and never read

**Severity: medium.** A moderation control that silently does nothing.

`packages/core/src/permissions.ts:422` and `:431` define:

- `requiresThreadApproval` — "New threads land as unapproved."
- `requiresPostApproval` — "New replies land as unapproved."

Both are real permission fields: negative-sense, AND-combined, forum-scoped,
editable on `/admin/groups/<id>` and on `/admin/forums/<id>/permissions`, and
resolved by the authorizer into the forum matrix.

**No write path reads either of them.** Creation decides visibility from the
*forum row's own columns* instead:

```ts
// packages/threads/src/reply.ts:167
(target.forum.moderateNewPosts && !input.bypassesModeration) || …
// packages/threads/src/compose.ts:283
(forum.moderateNewThreads && !input.bypassesModeration) || …
```

A repository-wide search for a consumer of `requiresPostApproval` outside the
registry, the fixtures and the seed finds none. (Its sibling
`requiresApprovalOnEdit` *is* wired, via `apps/forum/src/server/post-scope.ts:81`
— which is what makes the other two look wired too.)

### Reproduced

1. `/admin/groups/2` (Registered) → tick **"New replies land as unapproved"** → save.
2. Reload: the box is ticked. Database agrees:
   `usergroups.requires_post_approval = t` for id 2.
3. Sign in as a member of that group and reply to a thread.
4. The reply is **immediately public** — `posts.visibility = 'visible'`.
   The approval queue reads *"0 posts awaiting approval. Nothing is waiting."*

The per-forum control does work, and was verified in the same session: ticking
**"Hold new replies for approval"** on `/admin/forums/4` held the next reply as
`unapproved`, it appeared in the moderator's queue, selecting it and pressing
Approve published it (`visibility` → `visible`) and emptied the queue. So the
approval machinery is sound — only the group-level route into it is dead.

Either wire the resolved matrix into `reply.ts`/`compose.ts`, or remove the two
fields from the group and forum-permission screens. An operator who ticks a box
labelled "New replies land as unapproved" and gets no holding is worse than one
who never had the box.

## M4 — Plugin migrations can never be applied, and the panel tells operators to run a command that cannot apply them

**Severity: medium.**

With a plugin registered in `forum.config.ts`, `/admin/plugins` says:

> reference — **2 migrations not applied — run `forum upgrade`.**

and the plugin's own page is emphatic:

> **Run `forum upgrade` before relying on this plugin — until then its code is
> running against a schema that does not have what it expects.**

`forum upgrade` cannot do it. `apps/cli/src/index.ts:182` hard-codes:

```ts
return upgrade({
  dryRun: args.includes('--dry-run'),
  plugins: [],          // ← always
  log: (line) => console.log(line),
})
```

### Reproduced

Registered `plugins/reference`, restarted, then from the repository root — where
`forum.config.ts` is right there:

```
$ pnpm forum upgrade
Upgrading…
  1. apply pending core migrations
  2. record version 0.1.0
Core: already up to date.
Recorded version 0.1.0.
```

`/admin/plugins` still reads "2 migrations not applied". No table the plugin
declares exists. The warning is permanent.

The runner itself is fine — `apps/cli/src/upgrade.ts` orders plugins
topologically and applies each migration in its own transaction. It is simply
never handed any plugins, and **nothing else hands it any either**: the worker's
migrate role (`apps/worker/src/migrate.ts`) calls `runMigrations()`, which is core
only, and a repository-wide search finds no other caller of `upgrade()`.

The limitation is documented for the npm case in `docs/upgrading.md:309` and
`docs/deviations.md:6530` — "the runner is exported for the board's own entry
point" — but that entry point does not exist in the tree, and the two supported
deployments (Docker Compose and Coolify, per the README) both go through the CLI
or the worker. Meanwhile `docs/operating.md:919` states the opposite outright:

```
forum upgrade      # core, then plugins, then record the version
```

Three things need to agree: ship the board-side entry point, have the in-tree CLI
pass `forumConfig.plugins` when it can find a config, and stop the panel naming a
command that will not work.

## M5 — Creating a forum in the ACP leaves a stale tree when JavaScript is on

**Severity: medium.** Correct without JavaScript, wrong with it — which is
backwards from the failure mode this codebase usually guards against.

`apps/forum/src/server/forum-admin-actions.ts:210` (`createForumAction`)
invalidates the board's own cache and returns:

```ts
await invalidateTree()
await recordAdminAction({ action: 'forum.created', detail: { slug, type } })
return { notice: 'created' }
```

There is no `revalidatePath` and no redirect, so Next's client Router Cache keeps
serving the page it already has. The success notice renders (it is action state),
the new row does not.

### Reproduced — same script, JavaScript on and off

| | success notice | new row in the tree | after F5 |
|---|---|---|---|
| JS **on** | shown | **missing** | present |
| JS **off** | shown | present | present |

Three consecutive runs with JavaScript on, waiting three seconds each: row absent
3/3, present after reload 3/3.

The forum *is* created — this is a display bug, and a costly one, because the
operator's next move is to create it again.

The repository already has the fix and explains it, in
`apps/forum/src/server/redirect-back.ts`:

> A Server Action re-renders the route it was posted from, but the client Router
> Cache holds the **layout** … With scripting off, the browser's own 303 back to
> the same URL re-fetches everything and the change lands; with scripting on, the
> same button did nothing at all until you reloaded.

`redirectToCurrentPath()` after the write is the whole fix. Worth checking the
other ACP list writes that return a bare notice for the same shape.

## M6 — The Content-Security-Policy neither blocks nor reports

**Severity: medium.**

`apps/forum/next.config.mjs:143` sends:

```
Content-Security-Policy-Report-Only:
  default-src 'self'; img-src 'self' data: https:; style-src 'self' 'unsafe-inline';
  script-src 'self' 'unsafe-inline'; connect-src 'self'; frame-ancestors 'self'
```

Confirmed on the wire — the enforcing `Content-Security-Policy` header is absent.
Report-only enforces nothing, and with **no `report-uri` and no `report-to`** the
violation reports go nowhere either. As shipped the header has no effect of any
kind; the browser dutifully logged report-only violations to a console nobody
reads during this audit.

`script-src 'unsafe-inline'` would also remove most of the value even once
enforced, since that is what an injected `<script>` needs.

The sibling app knows better — `apps/web/next.config.mjs:67` reads *"Enforced
rather than report-only, which the board cannot yet manage."*

To be clear about the risk: **no XSS was found.** Every payload tried
(`<script>`, `<img onerror>`, `javascript:` in raw HTML and in markdown link
syntax, `<svg onload>`, `<iframe src="javascript:">`) came back as literal text —
0 `[onerror]` attributes, 0 injected `<script>`, 0 `javascript:` hrefs, 0 iframes
in the live DOM, both in post bodies and in signatures. The CSP is defence in
depth that is currently switched off, not a hole in itself.

The rest of the headers are good: `nosniff`, `X-Frame-Options: SAMEORIGIN`,
`Referrer-Policy: strict-origin-when-cross-origin`, HSTS two years,
`Permissions-Policy` denying camera/mic/geolocation.

## L7 — The installer's error box is invalid HTML and throws a hydration error

**Severity: low.** Only on the failure path — which is the path an operator is on
when they most need the page to work.

`AlertDescription` renders a `<p>` (`packages/ui/src/alert.tsx:76`). Inside one,
`apps/forum/src/components/install/install-form.tsx` puts a `<ul>` (line 525) and
another `<p>` (line 549). Both close the outer paragraph during HTML parsing, so
the DOM the browser builds is not the tree React rendered.

### Reproduced

Any failing install step. The browser console:

```
In HTML, <p> cannot be a descendant of <p>.
This will cause a hydration error.
<p> cannot contain a nested <p>.
```

The `role="alert"` sits on that outer `<p>`, so the truncation also cuts the field
list and the retype-your-password line out of the announced region — a screen
reader gets less of the failure than a sighted reader does.

`<div>` for `AlertDescription`, or moving the `<ul>` and trailing `<p>` out to be
siblings of it inside the `<Alert>`, fixes both.

## L8 — "Copy permissions from" is required, and omitting it says "No such group."

`apps/forum/src/components/admin/group-forms.tsx:325` marks the select `required`,
but the form is `noValidate` (line 304) — deliberate, so refusals come from the
server and read the same with scripting off. The server message comes from the
generic helper at `apps/forum/src/server/group-admin-actions.ts:37-41`:

```
Not saved. No such group.
```

for a field the operator simply has not touched. The field's own help text says
"Required. Starting from the defaults would deny everything" — the error should
say that, not imply the chosen group has vanished. Creating a group with the
select filled in works correctly and was verified.

## L10 — Signed-out visitors get 404 on some gated pages and a login redirect on others

Measured anonymously against the running board:

| Path | Anonymous response |
|---|---|
| `/modcp` | **307 → `/login?next=%2Fmodcp`** |
| `/messages` | **307 → `/login?next=%2Fmessages`** |
| `/usercp` | 404 |
| `/notifications` | 404 |
| `/subscriptions` | 404 |
| `/moderation` | 404 |
| `/admin` | 404 |

404 for `/admin` is a defensible choice — it does not confirm the panel exists.
The same argument does not apply to `/usercp`, `/notifications` or
`/subscriptions`, whose existence is not a secret and which are exactly the URLs
a member has bookmarked. Two of the seven already redirect; the split looks like
drift rather than a decision.

## What was tested and found working

Recorded so the report is a picture of the board and not only of its gaps.
Roughly 220 positive browser checks, all against real Postgres.

**Installer.** Renders on an empty database; refuses a short password and a
reserved username; applies 35 migrations; writes settings, the administrator and
the default forum; seals itself (`/install` → 404 afterwards); the board comes up
with the name that was typed and the owner reaches the ACP.

**Reading.** Index, forum display, thread view, member profile, reputation page,
all five `/discover` views, `/online`, `/stats`, `/jump`, `/search`, RSS and Atom
for board, forum and thread, sitemap, `robots.txt`, MyBB legacy URLs, 404s.

**Writing.** New thread, reply, inline quick reply, edit own post, preview, draft
save and restore-on-return, polls with voting, thanks/reputation, subscriptions,
empty-body refusal, flood control (verified by tripping it).

**Attachments and avatars.** PNG accepted, re-encoded through the queue, served
with `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` and
`Content-Security-Policy: default-src 'none'; sandbox`. `.php` and `.svg` refused
by name and type with a message that says which types are allowed.

**Search.** Keyword search over subject and body, replayable token URLs
(`/search/<token>`), a real "nothing matched" message, results re-checked against
the viewer's access on every open, per-scope filtering in the API.

**Moderation.** Lock (and a locked thread refusing a reply), pin, move (thread
appears in the destination), soft delete (hidden from members), reports from
member to queue, warnings with points, the approval queue end to end, the
moderator log recording every action, bans (group moved to Banned, ban row
written, posting refused).

**Control panels.** All 23 ACP pages render; the ACP demands the password again
before entry and times out separately from the board session; board settings save
and reach the board; forums, groups, users, announcements, anti-spam, themes,
system health, admin log all work; ModCP overview, forums, IP lookup and log;
UserCP profile, options, signature, avatar, contacts, password change (with the
correct refusal on a wrong current password), e-mail change behind a confirmation
link.

**Messaging.** Send, deliver, read, reply, forward, folders, quota, unknown
recipient refused by name, notifications raised, notification preferences saved.

**Themes and plugins.** Both themes listed and switchable per viewer, choice
persisting across navigation, light/dark/system applying to `<html>`. With the
reference plugin registered: enable/disable, UI contributions in every region,
26 hooks firing, its admin page mounted at `/admin/plugins/reference`, its
namespaced settings, its scheduled task registered, and posting still working with
its `post.created` handler in the path.

**REST API.** All seven endpoints; 401 without a token and with a bogus one, with
one message that does not say why; scope enforcement (a `forums:read` token gets
403 `missing_scope` on `/search`, `/me` and writes); `x-ratelimit-*` on every
response; 404 for unknown ids and unknown endpoints; `POST /threads/:id/posts`
returning 201.

**Security.** Session cookie `HttpOnly` + `SameSite=Lax`, `__Host-` prefixed and
`Secure` outside dev; logout invalidates server-side and the old cookie cannot be
replayed; no XSS anywhere tried; no open redirect via `?next=` (absolute, `//`,
`/\`) or `/redirect?to=`; cross-origin form POST to a server action refused with
the profile unchanged; registration honeypot (`contact_url`) plus a timing
challenge (`_issued`/`_challenge`); duplicate username and weak password refused;
password reset that does not disclose whether an address exists; and a full
permission matrix over 60-odd route/role pairs with no leak — members blocked
from `/admin` and `/modcp`, one member unable to read another's private message,
open another's post editor, or see another's UserCP.

**Background work.** `/api/system/tick` refuses without the secret (404, not 401),
runs all sixteen tasks with the secret, drains the queue, rolls up statistics,
re-encodes uploads, relays the outbox.

## Suggested order

1. **H1** — a stranger can lock the administrator out of their own board.
2. **H2** — four `new Date(...)` calls; until then a leaked token cannot be revoked.
3. **M3** — wire the two permission fields or take them off the screens.
4. **M4** — make `forum upgrade` match what the panel and `operating.md` promise.
5. **M5** — `redirectToCurrentPath()` after the ACP tree writes.
6. **M6** — enforce the CSP, drop `'unsafe-inline'` from `script-src` if it can be.
7. **L7–L10** — small, independent.

H2, and the latent one in `outbox-repo.ts`, argue for one more gate: the raw-SQL
repositories that claim `Date` are checked only by PGlite, which returns `Date`
where the real driver returns a string. `client.pg.test.ts` is the right home for
a read-direction case beside the write-direction one already there.
