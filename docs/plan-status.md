# Plan status

Feature-by-feature status against [`roadmap.md`](./roadmap.md). This is the
tracking file: **one row per plan feature, always**. `progress.md` says what to do
next in prose, `deviations.md` records decisions and divergences, and the roadmap
defines scope, dependencies, and acceptance criteria.

## How to use it

- Update the row in the **same PR** as the feature. A green gate with a stale row
  here is worse than no row.
- A feature is `DONE` only when its plan acceptance criteria are met **and** the
  Definition of Done holds. Anything else is `PARTIAL`, with the gap named in the
  row — never "mostly done".
- `PARTIAL` rows must say what is missing, not what is present. The missing half
  is the useful information.

## Legend

| Mark | Meaning |
|---|---|
| `DONE` | Acceptance criteria met and verified. Evidence column says how. |
| `PARTIAL` | Some of it exists. The gap is named explicitly. |
| `TODO` | Not started. Schema may exist — that is noted, and is not the feature. |
| `GATE` | A ⛔ gate. Nothing downstream starts until it is green. |

Reveal is **per post and additive**, in the query string, and a GET because it changes nothing; your own post is never hidden. **Staff cannot be ignored**, explicitly rather than silently — a moderator's post is often the one explaining why a thread was locked — resolved as `modcp.access` by the Authorizer and handed over as a boolean (F20), and asked only for an ignore so a buddy costs no actor build. The **PM block** folds into the same refusal as "your group cannot receive private messages": naming the ignore would make F60's send path an oracle for somebody's list, and MyBB's silent discard is worse than either because the sender believes they were heard; a *failed* block read answers true, because an unchecked ignore must not be a message that gets through. Buddy lists carry **online state**, which needed `users.last_active_at` to get its **first writer since `0000`** — `touchLastActive`, a conditional UPDATE whose throttle is the WHERE clause like `touchLocation`, called from the page shell. 33 tests, seven mutants killed (reveal applied per author, ignored posts filtered out of the page, the body still rendered, the staff check dropped, a trusted `returnTo` open redirect, a symmetric block, `created_at` replaced on re-list). See **D60** and three `mybb-parity.md` entries. *No board-wide online list (F75 owns it; `ONLINE_WINDOW_MINUTES` lives here as the only consumer), `PostAuthorModel.isOnline` still false for every post, and no ignoring a thread or forum (that is F56's verb). Fixture mode has no relation store (D38). |
| F62 | Reputation | `DONE`* | Migration `0013`: `reputation`, plus `can_give_reputation` and `max_reputation_per_day` on `usergroups` and four `reputation.*` board settings. **The two rate limits are two mechanisms, because they are two shapes.** "One rating per person per target" is uniqueness, so it is a partial unique index (D48's trick) — two clicks arriving together both pass a check-then-insert — and there are **two** indexes rather than one, because rating somebody's post is a different statement from rating them and collapsing the two would silently overwrite one with the other; re-rating *updates*, so changing your mind is supported rather than a way to stack points. "At most N a day" is a window, which no index expresses, so it is a count inside the writing transaction — and its residual race (N+1 for somebody scripting it) is stated in the migration rather than hidden. Revising an existing rating spends no allowance, because making a correction cost one would push people to leave a wrong rating alone. **`users.reputation` had no writer since `0000`; it gets one, and it is derived rather than incremented** — recomputed from the live rows in the same transaction as anything that changes them, like F53's `warning_points`, with a test that corrupts the column and watches it repair. A submitted `-1` on a board with negatives off is **refused, not clamped to +1**: quietly turning a criticism into praise is the worst reading of somebody's intent. `reputation.give` and `signature.use` are new global actions, so the F22 forum matrix is untouched. `/member/[id]/reputation` is the history and the form (paged, so its own route); the profile shows the summary; F31's postbit gains a Rate link carrying the post. 34 tests, seven mutants killed (the total incremented instead of recomputed, a negative clamped to positive, `parseRating('')` read as neutral — a real hole this found — a revision charged against the cap, post ratings collapsed onto the profile index, an unscoped withdraw, the post floor ignored). See **D62** and two `mybb-parity.md` entries. *No `reputationPower` multiplier: it cannot obey R4.2's numeric rule, the same shape as the `searchfloodtime` divergence. No leaderboard (F75), no reputation-gated permissions (two sources of truth for access is one nobody can reason about), and no notification on being rated — the kind would fire on every rating and needs a per-kind digest F55 has no shape for. Fixture mode has no reputation store (D38). |

| F63 | Admin CP foundation | `DONE`* | Migration `0015`: `admin_sessions`. `@forum/admin` holds the session policy, the allowlist and the log shapes; `PostgresAdminSessionRepository` and `PostgresAdminLogRepository` are the stores. **A second session, not a second account**: entering `/admin` re-enters the password and mints a session separate from the board's, with a 30-minute idle timeout and an **8-hour absolute ceiling** — the threat is an administrator's own browser being used by somebody else, and a board session lasts days by design, so an ACP session that inherited that would make an unattended laptop a takeover. The **allowlist is env, prefixes, and checked first**: env because it defends against a stolen credential and a setting could be edited by one; prefixes because a CIDR mask is a thing operators get wrong by one bit and the failure mode is being locked out; first because a request from outside it must not learn the panel exists — the ordering is pinned by a test in which a *guest* from a blocked address gets `address` rather than `permission`, written after mutation testing showed the first version did not pin it. reinterpreted unilaterally.

1. ~~**F03 vs invariant 32.**~~ **Resolved 2026-07-30:** invariant 32 governs.
   Forward-only; F03's "up and down" acceptance is superseded. A down migration
   that drops a column is a data-loss button on a live board, and some
   migrations (a destructive backfill) cannot be reversed at all, so the
   guarantee would be partial and therefore misleading. Recovery is by restore —
   F88's backup runbook is the documented answer.
2. ~~**F06 route path.**~~ Resolved: renamed to `/api/system/tick`, with
   `vercel.json` and the compose tick loop updated.
3. ~~**`forum.config.ts`**~~ **Done 2026-07-30.** Minimal registry (themes +
   plugins), read by `layout.tsx` so it is load-bearing rather than decorative,
   plus guard `R1 no-runtime-filesystem-scan` enforcing the half of invariant 6
   that actually bites on serverless. See D33.
4. ~~**Orphan forums in `buildTree`**~~ **Resolved 2026-07-30 at F29:** subtrees
   are filtered **whole**. A forum the viewer cannot see takes its descendants
   with it, because promoting a visible child to top level leaks the existence
   and name of a hidden category's children and makes the board's shape depend on
   who is looking. `buildTree` still promotes orphans — that is correct for a
   genuinely orphaned row — so the view model drops unreachable subtrees before
   building, iterating to a fixed point. See D38.
