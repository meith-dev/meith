# Plan status

Feature-by-feature status against [`roadmap.md`](./roadmap.md). This is the
tracking file: **one row per plan feature, always**. `progress.md` says what to do
next in prose, `deviations.md` records decisions and divergences, and the roadmap
defines scope, dependencies, and acceptance criteria.

## How to use it

- Update the row in the **same PR** as the feature. A green gate with a stale row
  here is worse than no row.
- A feature is `DONE` only when its plan acceptance criteria are met **and** the
  Definition of Done holds. Anything else is `PARTIAL`, with the gap named in the
  row — never "mostly done".
- `PARTIAL` rows must say what is missing, not what is present. The missing half
  is the useful information.

## Legend

| Mark | Meaning |
|---|---|
| `DONE` | Acceptance criteria met and verified. Evidence column says how. |
| `PARTIAL` | Some of it exists. The gap is named explicitly. |
| `TODO` | Not started. Schema may exist — that is noted, and is not the feature. |
| `GATE` | A ⛔ gate. Nothing downstream starts until it is green. |

| F46 | Anti-spam and flood control | `DONE` | `@meith/antispam` plus migration `0030` (`rate_limits`, `captcha_questions`). Four mechanisms, because each is weak alone and they fail to different attacks. **A limit is not an interval, and the board needs both**: F39's flood interval is a minimum *gap*, which a script satisfies forever by posting every 31 seconds — 2,800 posts by morning, each one within the rules. A limit bounds *how many in a window*; the interval stops a double-submit and the limit stops a night's work, and both are exempted by the same `flood.bypass`. **The counter is the write, and that one statement is the feature**: `insert … on conflict do update … returning`, so ten concurrent requests get ten distinct totals — a read-then-write hands all ten the same number and lets all ten through, which under an attack is the *expected* interleaving rather than a rare race, and is exactly what a single-threaded test cannot catch. Pinned by ten `Promise.all` consumes against real Postgres requiring `1..10`. It is also what makes the limit multi-instance in the roadmap's sense: the counter is a row, so ten serverless instances share one allowance. **There is deliberately no “check” method** — reading without spending is what a caller does just before forgetting to spend — and **a refused attempt still counts**, or an attacker who ignores the refusal gets a fresh decision every time and the window never fills. Fixed windows, not a sliding log: the boundary is an accepted failure (one extra window) and a row-per-action would make anti-spam the board's largest table. The prune looks **two** hours back, because a one-window boundary races the counter a live request is incrementing and resetting somebody's allowance mid-window is the one way the task could help a spammer. Wired at all five sites the roadmap names — uploads charged **per file** (a form-counted limit lets one post carry ten), reports charged **after** the permission checks (so probing cannot exhaust a real member's allowance, and a limit never answers “too many” where the honest answer is “that does not exist”), and draft saves charged not at all. **The captcha seam ships with no third party in it**: a hosted captcha is a runtime-dependency decision this project escalates *and* a decision about members — every visitor's browser contacting somebody else before they can join — so the port is here with `none` and admin-defined questions, and hCaptcha is a small module with no call site changing. `noCaptcha` is a real provider rather than a `null` callers check, so a form cannot silently lose its captcha. **The question challenge fails open**, the sharpest trade here: an empty list lets everybody through, because failing closed would lock registration behind a form refusing every answer including the right one, with the explaining screen on the far side. Answers are checked against **what is stored now** (a form carrying its own answer is one an attacker holds a copy of) and are **not hashed** — the question is public and an attacker learns the answer by registering once. The honeypot is the only default-on control, hidden from assistive technology and out of the tab order; the fill-time floor treats a missing or future stamp as a **pass**, since the stamp is attacker-controlled and refusing without it breaks real browsers to stop an attacker who deletes a field. **First-post moderation is a third reason to hold a post with its own bypass rule** — the warning still outranks `moderation.bypass` (F53), this follows the forum queue, or every newly appointed moderator's first post lands in the queue — and it reads a **post count, not an account age**, because age is satisfied by waiting and punishes the new member who posts immediately. **Everything fails open**: a nuisance control that closed on a database blip would stop every member posting to stop a spammer who is not trying. The challenge is verified **before** the rest of the form, or a refused submission becomes an enumeration oracle for taken usernames. Every default is inert but the honeypot. 49 tests. See **D100**. |

## Open questions for a human

Per [`roadmap.md`](./roadmap.md)'s working rules — these are not being
reinterpreted unilaterally.

1. ~~**F03 vs invariant 32.**~~ **Resolved 2026-07-30:** invariant 32 governs.
   Forward-only; F03's "up and down" acceptance is superseded. A down migration
   that drops a column is a data-loss button on a live board, and some
   migrations (a destructive backfill) cannot be reversed at all, so the
   guarantee would be partial and therefore misleading. Recovery is by restore —
   F88's backup runbook is the documented answer.
2. ~~**F06 route path.**~~ Resolved: renamed to `/api/system/tick`, with
   the compose tick loop updated.
3. ~~**`forum.config.ts`**~~ **Done 2026-07-30.** Minimal registry (themes +
   plugins), read by `layout.tsx` so it is load-bearing rather than decorative,
   plus guard `R1 no-runtime-filesystem-scan` enforcing the half of invariant 6
   that actually bites on serverless. See D33.
4. ~~**Orphan forums in `buildTree`**~~ **Resolved 2026-07-30 at F29:** subtrees
   are filtered **whole**. A forum the viewer cannot see takes its descendants
   with it, because promoting a visible child to top level leaks the existence
   and name of a hidden category's children and makes the board's shape depend on
   who is looking. `buildTree` still promotes orphans — that is correct for a
   genuinely orphaned row — so the view model drops unreachable subtrees before
   building, iterating to a fixed point. See D38.

5. ~~**A MySQL client, for F85's importer.**~~ **Resolved 2026-08-03: `mysql2`,
   loaded dynamically inside `connect()`, recorded as
   [ADR 0004](./adr/0004-mysql2-import-reader.md).** The original text follows.

   *Was: open, and blocking the last third of F85.* Reading a live MyBB board means talking to MySQL, and every client is a
   **runtime dependency** — which the roadmap's working rules say to stop for a
   human on. F85 therefore ships the source *port*, a fixture implementation, and
   every decision that is not "connect to MySQL": the mapping, the ordering, the
   chunking, the resumability, the idempotency and the counter comparison. A
   reader is `SELECT * FROM mybb_posts WHERE pid > ? LIMIT ?`.

   Three options, and they are genuinely different rather than shades of one:

   - **`mysql2`** — the obvious choice, widely used, and the dependency is only
     ever loaded by the import command. It is not in the request path and not in
     the serverless bundle unless the importer is.
   - **A dump reader.** An operator exports `mysqldump` and the importer parses
     the file. No database dependency at all and it works against a board that is
     already switched off, which is the safer migration anyway — but somebody has
     to write a MySQL dump parser, and doing that badly is worse than a driver.
   - **A separate tool**, published apart from the board, that reads MyBB and
     writes this board's REST API (F81). Keeps the dependency out of the board
     entirely; costs an import that is as slow as HTTP and needs a token with
     write scopes that do not exist yet.

   The recommendation is `mysql2` behind the existing port, but it is a runtime
   dependency and the rule says a human decides.

6. ~~**Bounding search relevance, for F89's one budget violation.**~~
   **Resolved 2026-08-03: bound the window.** Relevance now ranks the 20,000
   most recent matches; newest/oldest still read the whole corpus, because
   `order by id` is indexed and stops after twenty rows however many match.
   Re-measured on the same 2,343,847-post board: **5,486 ms → 98 ms**, a 56×
   improvement, and `search-common` went from a `limit` to a 300 ms target that
   uses 33% of its budget. Identical results for any term matching fewer than
   20,000 posts, which is every real query. Recorded in `mybb-parity.md`.

   The accompanying half of the recommendation — a Zipfian seeder vocabulary, so
   the scenario measures a plausible worst case rather than a sixteen-word
   artefact — is **not done**. It is now a fidelity improvement rather than a
   blocker: the pathological term is fast enough that a realistic one is
   certainly fine, so the scenario over-measures and no longer hides anything.
