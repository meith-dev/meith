# Run multiple web instances

Multiple web instances must share PostgreSQL, a Redis-compatible cache and uploaded files. Prepare those shared services before adding replicas.

## Understand what is shared

Sessions, rate limits, queues and scheduled-task claims live in PostgreSQL. Requests do not need sticky sessions. Workers can claim work concurrently without treating every replica as an independent queue.

Process-local caches and local disks are different: another server cannot see an upload on the first one's disk, and local cached settings can lag after changes. Metrics are also per process and must be aggregated.

## 1. Prepare shared cache and storage

Set `CACHE_DRIVER=redis` and `REDIS_URL` for the compatible server. Redis holds cache entries; PostgreSQL remains the durable source. Losing Redis does not delete posts, but an unavailable configured cache can fail requests, so monitor it as required infrastructure.

Choose shared upload storage. Replicas on one machine may share a persistent volume. Across machines, configure an S3-compatible store with its bucket, region, credentials and optional endpoint. Back up before moving existing uploads.

## 2. Migrate an existing instance

1. Start the shared cache and verify connectivity.
2. Copy existing uploads to the intended shared store, preserving keys.
3. Change the board's cache and file-store environment.
4. Recreate the existing web instance and verify old attachments and a new upload.
5. Add replicas only after that instance works with the shared services.

Keep the original upload copy until the migration is verified. Switching a driver does not copy files automatically.

## 3. Configure the proxy and replicas

For the generated by-hand Compose stack, the `redis` profile supplies a compatible cache. Configure the reverse proxy on the service network if scaling the web service: a fixed host port cannot be bound by several containers.

```sh
docker compose --profile redis up -d --build
docker compose --profile redis up -d --scale web=3
```

Use this only after adapting the proxy/port configuration and environment. Route to the web service without session affinity. Keep `TRUSTED_PROXY_HOPS` equal to the number of trusted proxies, not the number of web replicas.

## 4. Budget database connections

Each application process has its own pool. Multiply the per-process limit by potential web instances and include workers and maintenance commands. Use runtime pooling where appropriate and the direct connection for migrations and backups.

Read [Database connections](database-operations.md). A burst of function instances can exhaust a database or cache connection limit even when one test instance works.

## 5. Verify across instances

Change a setting, read it through another instance, upload a file and retrieve it through another instance, then check sign-in and private-forum visibility. Watch queues, errors and database connections under realistic load.

[Monitoring](monitoring.md) explains per-instance metrics. [Vercel configuration](vercel-configuration.md) covers function hosting; it is not the same deployment as scaling a persistent Compose service.
