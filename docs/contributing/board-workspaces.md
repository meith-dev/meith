# Board workspaces

## The workspace

| Path | Package/use |
|---|---|
| `apps/community` | `@meith/web`; development board and published framework |
| `apps/web` | `@meith/site`; project website |
| `boards/stock` | Board built into the official image |
| `themes` | Default, Midnight, Phasebook, Raidframe, Clubhouse and Meith |
| `plugins` | First-party plugins, including Dues, Calendar, Awards and the reference example |
| `examples` | Source for generated plugin/theme tutorials |

A board owns `meith.config.ts`, its plugin manifest and generated registry. Framework code accesses those through `@board/*`, not relative imports into a particular board.

## Consuming the board from a workspace

The `forum-web` and `meith` bins materialize framework sources into `.meith/app` and `.meith/cli`, configure `@board/*` aliases, then invoke Next.js or tsx. Build stages static/public files into the standalone output; start runs that output.

Generated standalone boards use npm's hoisted dependency layout. The Meith pnpm workspace uses its configured aliases. Keep reachable framework packages in the appropriate transpilation/externalisation configuration.

The default source layout assumes two directory levels. `--at-root` and `FORUM_WORKSPACE_ROOT` support the alternate root layout. SWC helper tracing supports the checked isolated and hoisted layouts; update its version checks when changing the dependency.

## Materialized files

The at-root manifest `.meith/materialized.json` records owned files. Existing files are replaced only when ownership or exact generated bytes establish that they belong to the framework. Conflicting board files stop materialization.

Generated TypeScript configuration and Next environment files are overwritten. Stale owned files are removed; foreign files are retained and reported. Public assets are tracked per file so board additions survive.

Keep custom application code outside generated framework directories. Never edit `.meith` as the source of a customisation.

## Plugin manifests

`apps/community` and `boards/stock` use matching manifests, registered in `scripts/boards.json`. Add dependencies to both where required, then run `pnpm board:gen`. The generator owns `meith.plugins.ts` and validates the manifest shape.

`MEITH_BOARD_PLUGINS_ROOT` supports generator tests. `DUES_TEST_BOARD=1` adds test plugin definitions and local overrides through `meith.test.plugins`; it is not production configuration.

## Change the framework

Keep Next.js versions aligned across framework peers, scaffold and driver manifests. Regenerate the board installer and update the pnpm lockfile. Deploy template snapshots change during releases.

Validate packaging changes with `pnpm board:workspace:smoke` and extension changes with `pnpm extension:workspace:smoke`. These pack local dependencies and test generated consumers, including root materialization, styles and public assets.

Fixture builds still require the configured auth secret. Writable boards require PostgreSQL and a scheduler. Scaffolded workers call the board's HTTP task endpoint; the monorepo worker is a separate process.
